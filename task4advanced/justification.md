# Обоснование событийного подхода относительно старой схемы Camel ESB/DWH

## Проблемы текущей архитектуры

1. DWH помимо хранения аналитических данных выполняет функции интеграции сервисов. Бизнес-логика всех доменов сосредоточена в хранимых процедурах SQL Server 2008. 

    Последствия:
    - DWH становится узким местом и единой точкой отказа. Любое изменение бизнес-логики какого-либо домена требует изменения хранимых процедур DWH.
    - DWH сильно перегружено, отчеты выполняются очень долго.

2. MS SQL Server 2008 - устаревшая проприетарная система.

    Последствия:
    - Высокая стоимость владения.
    - Отсутствуют обновления безопасности.

3. MS SQL Server 2008 не способно масштабироваться горизонтально по определению.

    Последствия:
    - Производительность будет деградировать все сильнее и сильнее по мере увеличения объема хранимых  данных.

4. Используется ESB в которой все системы жестко связаны друг с другом фиксированными маршрутами.

    Последствия:
    - Еще одна единая точка отказа.
    - Маршруты Camel синхронные, при сбое в одном сервисе прерывается вся цепочка.
    - Нет единой схемы данных - каждый маршрут уникален.
    - Большая сложность поддержки.

5. Интеграция оранизована с использованием двух компонентов.

    Последствия:
    - Вероятность сбоя, затрагивающего все системы, увеличивается, так как каждый из этих двух компонентв является единой точкой отказа.
    - Сложность добавления новых сервисов - надо вносить изменения в оба компонента

## Преимущества событийного подхода

1. Слабая связность между доменами. Домены не знают о существовании других доменов. Взаимодействия асинхронные через Event Bus. При добавлении нового домена, если добавляется новый подписчик, изменять продюсер не требуется.

2. Хорошая масштабируемость при добавлении новых бизнес-направлений. Добавляем новый домен, не затрагивая существующие домены. В EventBus добавляется новый топик. Сервис аналитики автоматически подписывается на новый источник данных.

3. Аналитические данные поступают в новую DWH не батчами, а потоком. Данные всегда актуальны, а не устаревшие с момента последней батч-загрузки.

4. Устойчивость к сбоям за счет асинхронных взаимодействий.

5. Нет потери сообщений в случае сбое на стороне потребителя, Kafka позволяет перечитать события с любого момента.

6. Независимость команд разработки от команды, поддерживающей интеграционные сервисы.
